# AGENTS.md

Personal Codex plugin marketplace. Codex is the only consumer: nothing here is written for Claude Code or any other agent.

## Layout

```
.agents/plugins/marketplace.json   # Marketplace registry; `name` is the install suffix (base@codex-plugins)
plugins/base/                      # The one plugin
  .codex-plugin/plugin.json        # Manifest; `version` drives cache refresh
  skills/<name>/SKILL.md           # Skills, invoked as $base:<name>
  skills/<name>/agents/openai.yaml # UI metadata and invocation policy
  skills/<name>/scripts/           # Helpers used by that one skill, plus its test-*.sh
  scripts/lib/                     # Helpers shared by skill scripts (bash sourced, jq via -L, GraphQL via cat)
  hooks/hooks.json                 # Event hooks (default path, declare in the manifest only to move it)
  .mcp.json                        # MCP servers (declare as `mcpServers` in the manifest)
scripts/validate-manifests.py      # Manifest and SKILL.md checks; Codex has no `plugin validate`
THIRD_PARTY_NOTICES.md             # Source, license, and derived paths of adapted skills
```

## What the files do not say

- Codex identifies a plugin by its directory name. `plugins/<dir>`, `name` in `plugin.json`, and `name` in `marketplace.json` stay identical; renaming the marketplace breaks every `base@codex-plugins` install
- Codex caches a plugin under `~/.codex/plugins/cache/codex-plugins/<plugin>/<version>/`, so every change to a plugin bumps the patch number of `version` in its `plugin.json` (`0.2.0` → `0.2.1`), never the major or minor — the number only has to differ, the same way as in `kkhys/claude-code-marketplace`
- Codex shows the model each skill as `base:<name>: description (file: <root>/<skill>/SKILL.md)` — plugin skills carry the plugin name as prefix in the list — with the root resolved to an absolute path, so a skill body refers to its own files with plain relative paths (`scripts/post-pr-review.sh`) after one line saying paths are relative to the skill's directory. The user's explicit mention is `$base:<name>` (the `$` picker inserts that form); cross-references inside a skill stay `$<name>`, which Codex resolves as long as the bare name is unique, and which keeps the skills working if they are ever installed outside the plugin. Scripts are run through their interpreter (`bash scripts/x.sh`) because the executable bit is not guaranteed to survive installation. Nothing is substituted in a body: no `$ARGUMENTS`, no dynamic command output. The user's message is the argument ("the PR named in the request, otherwise the current branch's PR")
- Of a skill's frontmatter Codex reads only `name`, `description`, and `metadata.short-description`. `description` is one line, under 1024 characters, without angle brackets; it states the capability, when it applies, and one boundary when a neighbouring skill would otherwise be picked. Keep it discriminating: no trigger-phrase lists
- A skill refers to another skill as `$name`; keep the chain in one direction. `publishing-pr` runs `creating-branch-name` → `splitting-commit` → `creating-pr`; `splitting-commit`, `fixing-review-comments`, `diagnosing-ci-failure`, and `babysitting-pr` commit through `formatting-commit`; `fixing-review-comments` starts with `reading-unresolved-pr-comments` and hands resolution to `resolving-pr-comments` only on request — `babysitting-pr` is the one caller that resolves the threads it addressed without asking; `reviewing-pr` runs its own `references/review-pass.md` per lens (in subagents when available) and posts through `posting-pr-review` only on request; `diagnosing-ci-failure` and `merging-renovate-prs` reuse `babysitting-pr`'s `scripts/pr-watch.sh` and `references/ci-heuristics.md` through `../babysitting-pr/` — keep those paths stable; `creating-stacked-pr` owns the stack-or-not verdict and sends command mechanics to the external `$gh-stack` skill (installed in `~/.agents/skills` by the dotfiles) and conflicts to `resolving-merge-conflicts`; `merging-renovate-prs` merges only in repositories owned by `kkhys` and confirms each merge with the user — a sandbox escalation is answered by the auto-review model, not the user, so it never counts as that confirmation
- `recording-pr-qa` drives headless Chrome through `playwright-cli` (mise's `npm:@playwright/cli`), which reaches its browser daemon over a Unix socket under `$TMPDIR`. The sandbox denies that connection, and the client that fails to connect unlinks the socket and ends the session, so the skill runs every `playwright-cli` call with escalation — keep it that way. Retina density comes from Chrome's `--force-device-scale-factor=2` with `contextOptions.viewport: null` and no `resize` — not from a CSS zoom, which misplaced everything the app positions from a measured rect. `scripts/qa-overlay.js` is the context init script: it leaves the page alone and draws into the top layer the caption card, a checklist that `plan` lists and `check` ticks, a console hidden unless a case asks for it, a progress bar of one segment per chapter, its own pointer and click rings (Playwright's pointer is off, so `showActions` goes through `run-code`), keycaps, a scroll rail, a device stage for mobile and narrow widths (`__qa.device`: the page in a same-origin frame, whose copy of the script only relays events to the top overlay) and a closing card with confetti; `window.__qa` is its API, covered offline by `scripts/test-qa-overlay.sh` in a node vm. `--video-only` stops after the MP4. Screenshots go into the report folded in one `<details>`; the video stays open. Playwright stays the driver on purpose: agent-browser (0.42) takes Retina screenshots but its video is the CDP screencast at 1x, stretched to the device size, and it has no action callouts or clock. On a PR the user reviews (`--review`, or an author other than the viewer) the `## Manual QA` section goes into the user's pending review through `scripts/place-qa-review.sh`: `gh pr review` has no `--attach`, so the script uploads to the endpoint behind it (`POST https://uploads.github.com/user-attachments/assets`, push access required), rewrites the references, and updates the user's one pending review — `posting-pr-review` may have made it — or creates one; `scripts/test-place-qa-review.sh` covers it against a gh stub
- `recording-qase-qa` wraps `recording-pr-qa` for a repository that keeps its test cases in Qase. It reads that skill's file through `../recording-pr-qa/SKILL.md` and runs its steps by number — 1 to read the change, 2 to 5 to record, 6 to place, 7 to clean up — keep that path and those numbers stable. The Qase side goes through `scripts/qase-api.sh` (`QASE_API_TOKEN`, sent on curl's stdin; `--all` follows list offsets; `upload` sends attachments), run with escalation for the network; the token reaches the shell because `shell_environment_policy.ignore_default_excludes` defaults to `true` — a config that sets it to `false` filters the variable out. The Qase case ID is the thread: the change is mapped to the cases of the suites its Impact Scope names, each classed automated (wrapped by `qase(` in a spec of that project, so CI runs it), record, manual (left untested in the run: QA's share) or new; a missing case is written by `writing-qase-cases`, and the run's description lists the cases the PR made (`Created cases:`), which lets a rerun delete those and no others — the case itself carries nothing of the PR. The run is the one QA works in, and its URL reaches the PR body only after the recording and the spec's local runs, because a workflow that reads it there starts the automated cases on the same test account, where E2E runs are kept one at a time; for the same reason the spec PR's body carries no run URL. Every case is a chapter: `qa.sh` writes the clock before each one, and `scripts/cut-case-clips.sh` cuts the take into a clip per case, attached to that case's result with a status per Qase step. A recorded case that passed and leaves the shared test data alone becomes a spec through the repository's own E2E skill, shipped once it holds `--repeat-each=3`, on a PR stacked on the feature branch through `creating-stacked-pr` (`gh stack init <head> <spec branch>` adopts the PR's branch). Three confirmations gate every write — the cases and the run, the results and the PR body, the spec PR — and a sandbox escalation is none of them. Project facts — the project code, the suites, the spec conventions — are read from the repository; miitel-softphone is the named example
- `writing-qase-cases` is the rule for a case's content — only what lasts as long as the behaviour; variants as single, group or shared parameters; the PR, the ticket, a feature flag and the environment in the run or the result instead. It stays implicit and separate from `recording-qase-qa` because cases are also written outside that flow, through a Qase MCP tool or by hand
- `agents/openai.yaml` carries `interface.display_name`, `short_description` (25–64 chars), and a `default_prompt` that names `$skill`. `policy.allow_implicit_invocation: false` only for a user-timed workflow (`publishing-pr`); a skill with side effects stays discoverable and asks before the mutation instead
- Every comment the scripts post to GitHub starts with `[from Codex]`, so reviewers can tell an agent's comment from the user's own. `post-pr-review.sh` and `reply-to-review-threads.sh` prepend it idempotently (`scripts/lib/attribution.jq`) — write bodies without it; add it by hand on a plain `gh pr comment`. The exceptions are `illustrating-pr`'s picture section and `recording-pr-qa`'s `## Manual QA` section, in the PR body or in the user's pending review: both are the user's own material, vetted before placement, so they carry no marker
- Skill scripts resolve the shared lib relative to their own path (`"${SCRIPT_DIR}/../../../scripts/lib"`); the layout under the plugin cache is the same as in this repo, so the path holds after install
- Hooks are trusted per handler by a hash of its content, and plugin hooks are never trusted automatically: after changing a handler, re-trust it with `/hooks` in Codex. Events: `SessionStart`, `SessionEnd`, `UserPromptSubmit`, `PreToolUse`, `PermissionRequest`, `PostToolUse`, `PreCompact`, `PostCompact`, `SubagentStart`, `SubagentStop`, `Stop`, `Interrupt`
- `.mcp.json` ships only servers every Codex session may want; today that is `serena`, started through `uvx` from its git repository pinned to a release tag (the server runs outside the sandbox with the user's permissions, so the pin moves only on purpose, with a plugin version bump) with `--context=codex` (Serena then hides the file, search, and shell tools Codex already has) and `--project-from-cwd`. A repository that does not need it sets `[plugins."base@codex-plugins".mcp_servers.serena] enabled = false` in its `.codex/config.toml`; the same table takes `enabled_tools` / `disabled_tools`. Documentation lookup and browser automation belong to the projects that use them, not here
- Skills ported from another project record the source, its license, and the derived paths in `THIRD_PARTY_NOTICES.md`

## Checks

Before committing, `python3 scripts/validate-manifests.py` passes, `find plugins -name '*.sh' -print0 | xargs -0 -r shellcheck` is silent, and every `test-*.sh` under `plugins/*/skills/*/scripts/` and `plugins/*/scripts/` passes. CI runs all three on pull requests and pushes to `main`; new test scripts need no CI change.

Bash scripts start with `#!/usr/bin/env bash` and `set -euo pipefail` (sourced libs set no options); Python scripts are stdlib only.

## Git

- Commits follow Conventional Commits with the plugin name as scope (`feat(base): …`); root changes omit the scope
- Pull requests are drafts titled `[main] <type>: <description>` and assigned to `kkhys`
